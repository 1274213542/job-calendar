## 数据结构

- `updatedAt`：最后编辑日期；`timezone` 固定 `Asia/Tokyo`。
- `opportunities`：每个项目／批次一条；`id` 为稳定标识，不因修改名称、时间或状态重建；`company`、`title` 为显示名称。
- `category`：`activity`（说明会、讲座、反馈等）、`internship`（实习／工作坊）、`selection`（正式选考）、`personal`（已确认的非设计个人占用，不作为设计机会推荐）。`subtype` 是补充标签。活动平台的“応募済み”和正式选考提交是不同状态，必须看 `statusDetail`。
- `status`、`statusDetail`：分别存简明状态与证据／限制；未确认的预Entry、报名、录取及预约不可擅自升级。`description` 为地点、材料、报酬等信息，`nextAction` 为下一步，`notes` 记录日期说明、冲突或未知项。
- `sources`：`label` 必填；安全且合适的公开链接存 `url`。私人邮件或平台消息只用文字描述来源，不带原文、带token的链接或个人信息。`checkedAt` 记录最近一次查证。
- `milestones`：一个项目可有多个节点。`type` 为 `open`、`deadline`、`es_deadline`、`portfolio_deadline`、`test_deadline`、`confirmation_deadline`、`event` 或 `other`；`label` 解释场次及具体含义。`date` 为 `YYYY-MM-DD` 或日本当地 `YYYY-MM-DDTHH:mm`；未知钟点不补 23:59 或 00:00。`endDate` 为实际结束；若只有日期，其末日包含在活动期间内。`completed: true` 表示相应操作已完成，不应作为未完成行动。
- 报名窗口用同一项目的开放及截止节点组合。只知“已开放”但没有日期，不虚构开放节点；没有截止日期须在 `notes` 中区分未公布与 MyPage 待核。多场活动分别列节点；每个候选场不等于本人都将参加。

## 更新流程

收到新信息后先查来源、时间和状态，按稳定 `id` 修改已有项目；不同活动和正式岗位拆开记录，必要时追加新项目。记录证据、`checkedAt` 和 `updatedAt`；有冲突保留多个来源及差异，不覆盖成推测结论。编辑后检查 JSON 合法性、节点及状态，然后本地运行并核对日历、时间轴、手机显示。GitHub 提交与 Pages 部署需在用户指定仓库及明确授权后另行操作；本地编辑不等于已同步或公开。
